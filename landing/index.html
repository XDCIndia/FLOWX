How it works

From wallet to confirmed transfer in three calls.

No banking integrations, no ledger plumbing — FlowX handles the moving parts behind one REST API.

01 · POST /v1/wallets

Create a wallet

One call returns a 0x address on the XDC testnet. The private key is generated and encrypted inside FlowX — you only ever see the public address.

02 · POST /v1/transfers

Send a transfer

Attach an Idempotency-Key and get 202 Accepted instantly. The transfer moves through an async pipeline — no blocking, no timeout risk.

03 · Settle & track

Settle on-chain

The settlement worker signs and submits native TXDC. Poll GET /v1/transfers/:id or wait for a signed webhook: pending → confirmed (or failed).

FAQ

Questions, answered.

Walkthroughs and quickstarts live in the repo docs — or open a discussion on GitHub.

Is FlowX live?

The API is live on Apothem, the XDC testnet (Chain ID 51), and the repo is open source under MIT. Mainnet rollout is on the roadmap behind a swappable chain backend.

How are private keys secured?

Wallets are generated inside FlowX and every secret is encrypted at rest with AES-256-GCM. Keys are never returned by the API — you only ever hold the public 0x address.

How do you stop funds moving twice?

Every state-changing request takes an Idempotency-Key. If a call times out, retry it with the same key — the platform guarantees a transfer is only ever created once.

What does settlement look like?

An async worker signs and submits native TXDC on-chain, tracking confirmations and recording hashes. You watch transfers via polling or signed webhooks: pending → confirmed or failed.

Can I self-host FlowX?

Yes — MIT licensed and free. The repo ships a Docker Compose stack (Go API, PostgreSQL, Redis) plus the React dashboard and TypeScript SDK.
